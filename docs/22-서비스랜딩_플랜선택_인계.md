# 22. 서비스 랜딩 사이트 작업용 — 플랜 선택 부분 인계

작성일: 2026-07-31
목적: 지금 `apps/web` 안에 임시로 구현되어 있는 `/pricing`, `/signup` 화면은 "실제 마케팅 랜딩 페이지가 생기기 전까지의 스탠드인"이라고 코드 주석에 명시되어 있음. 서비스 랜딩 사이트를 실제로 만들 때, 여기 있는 로직(플랜 정의·가격 계산·가입 연동 흐름)을 그대로 가져다 쓰고 디자인만 새로 입히면 된다. 이 문서는 그 이식 작업을 위한 참고 정리.

---

## 1. 지금 어디에 뭐가 있는지

| 역할 | 파일 |
|---|---|
| 플랜 정의(라이트/스탠다드/어드밴스드, 프롬프트 상한, 모델 개수, 브랜드 개수, Stripe Price ID) | `packages/lib/src/billing/plans.ts` |
| 가격 계산(월액/연액 + add-on 합산) | `packages/lib/src/billing/plan-selection.ts` |
| 플랜 선택 UI(현재 임시 랜딩 화면) | `apps/web/src/routes/pricing.tsx` |
| 가입 폼 + 플랜 정보를 이어받아 체크아웃 시작 | `apps/web/src/routes/signup.tsx` |
| 가입 계정 생성 서버 함수 | `apps/web/src/server/signup-stripe-customer.ts` |
| 체크아웃 세션 시작 서버 함수 | `apps/web/src/server/billing.ts`의 `startCheckoutFn` |

## 2. 화면 흐름 (지금 임시 구현 기준)

```
/pricing (플랜 카드 3개, 월/년 토글, add-on 체크박스)
   │  "このプランを購入" 버튼 클릭
   │  → navigate({ to: "/signup", search: { plan, annual, promptAddonEnabled } })
   ▼
/signup (이름/회사명/이메일/비밀번호 입력 폼)
   │  제출 시:
   │  1. signupStripeCustomerFn() — 계정 + 조직 생성
   │  2. plan이 있으면 startCheckoutFn() 호출 → Stripe Checkout URL로 즉시 리다이렉트
   │     (plan이 없으면 /app/billing/select-plan으로 — 이건 랜딩 사이트와 무관, 로그인 후 플랜 미선택 상태 케어용)
   ▼
Stripe Checkout (호스팅 페이지, 카드 입력)
   ▼
/app/billing/success (결제 완료 후 온보딩 안내)
```

**핵심 포인트**: 비로그인 방문자는 가입 전에 결제를 못 하므로(계정이 있어야 Stripe Customer가 생기니까), `/pricing`에서 고른 플랜/결제주기/add-on 여부를 **URL 쿼리 파라미터로 `/signup`까지 그대로 들고 간 뒤**, 가입이 성공하자마자 그 값으로 체크아웃을 자동 시작한다. 랜딩 사이트를 새로 만들 때도 이 "플랜 선택 → 가입 → 자동 체크아웃" 순서 자체는 그대로 유지하는 게 맞다(방문자가 두 번 플랜을 고르게 하지 않기 위함).

## 3. 가져다 쓸 로직 (그대로 재사용 가능)

- **`STRIPE_PLANS`** (`plans.ts`): 플랜 이름, `maxPrompts`/`maxModels`/`maxBrands`, Stripe Price ID(월/연/+add-on 버전)가 이 배열 하나에 다 들어있음. 랜딩 페이지 카드 3개를 렌더링할 때 이 배열을 그대로 순회하면 됨 — 가격/한도가 바뀌어도 이 파일 하나만 고치면 랜딩까지 자동 반영됨.
- **`calculatePlanTotal()`** (`plan-selection.ts`): 월액/연액 + add-on 합산 금액 계산. 화면 디자인이 바뀌어도 이 함수 그대로 호출해서 표시 가격만 뽑아 쓰면 됨.
- **가입→체크아웃 연동 방식**(쿼리 파라미터로 plan/annual/promptAddonEnabled 전달): 새 랜딩 사이트가 `/pricing`을 대체하더라도, 최종적으로 `/signup?plan=...&annual=...&promptAddonEnabled=...` 형태로 넘기기만 하면 나머지(가입, 체크아웃 시작)는 손댈 필요 없음.

## 4. 디자인만 새로 입히면 되는 부분

`pricing.tsx` 자체의 마크업(Card 3개 그리드, 월/년 토글 버튼, add-on 체크박스, "このプランを購入" 버튼)은 순수 임시 UI라서 실제 랜딩 사이트 디자인 시스템에 맞게 완전히 새로 그려도 무방하다. 다만 아래 데이터/동작만 그대로 유지:

- 3개 플랜 각각의 이름(LIGHT/STANDARD/ADVANCED), 프롬프트 상한, 모델 개수 — `plan.maxPrompts`, `plan.maxModels`에서 그대로 읽어옴
- 월/년 토글에 따른 가격 변화 — `calculatePlanTotal({ plan, annual, promptAddonEnabled })`
- "+10件追加" add-on 체크박스와 그 가격 표시(`PROMPT_ADDON_FIXED_JPY`, 연간이면 ×12)
- 버튼 클릭 시 `/signup`으로 `plan`/`annual`/`promptAddonEnabled`을 넘기는 부분

## 5. 참고: 가격 하드코딩 위치 (중복 주의)

`plan-selection.ts`의 `MONTHLY_PRICE_JPY`/`ANNUAL_PRICE_JPY`는 **표시용 가격**이 별도로 하드코딩되어 있고, 실제 결제 금액은 `plans.ts`의 Stripe Price ID(Stripe 대시보드에 등록된 실제 가격)로 결정된다. 즉 가격을 바꿀 때는 **두 곳을 다 맞춰야 함**(표시용 숫자 + 실제 Stripe Price). 랜딩 사이트를 새로 만들 때 가격을 다시 하드코딩하게 된다면 이 이중 관리 함정을 그대로 물려받지 않도록, 가능하면 `plan-selection.ts`를 계속 단일 출처로 import해서 쓰는 편을 권장.

## 6. 서비스 랜딩이 별도 앱/배포가 아니라는 점 재확인

21번 문서에서도 조사했듯, 현재 이 프로젝트에는 별도 마케팅 앱(`apps/marketing` 등)이나 Vercel 배포 설정이 없다. `/pricing`, `/signup`은 `apps/web` 안의 라우트일 뿐이다. 향후 진짜 서비스 랜딩을 별도 앱/도메인으로 분리할지, 계속 `apps/web` 안에 둘지는 이 문서의 범위 밖이며 별도 결정 필요 — 다만 어느 쪽이든 위 3~5절의 로직은 그대로 재사용 가능하다.
